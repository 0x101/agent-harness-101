## In one paragraph

SWE-agent's authors argue that language model agents are a new kind of user and need their own interface, the **agent-computer interface (ACI)**: the commands the agent can use and how results come back. Instead of a bare Linux shell, their agent gets a few commands for viewing, searching and editing files, with guardrails such as a syntax check on every edit. With the same model, it fixes more real GitHub issues than the shell, and removing parts one at a time shows which matter.

- **Skim:** [Section 5.2](https://arxiv.org/html/2405.15793#S5.SS2), and the appendix on the [file editor](https://arxiv.org/html/2405.15793#A1.SS1.SSS0.Px2), for S08.
- **Skip:** related work ([Section 6](https://arxiv.org/html/2405.15793#S6)) and the case studies ([Appendix D](https://arxiv.org/html/2405.15793#A4)).
- **S04, Interfaces matter.** For each principle in Section 2, find the line in `harness/agent.py` that breaks it. Then guess which Table 3 ablation matters most on your tasks.

## What it shows

All three are measurements on SWE-bench, real GitHub issues from Python projects.

- **The interface beats the shell.** With GPT-4 Turbo on SWE-bench Lite, SWE-agent resolved 18.00% of issues and a shell-only agent 11.00% (Table 1, in [Section 4](https://arxiv.org/html/2405.15793#S4)).
- **Each part can be measured.** On Lite with GPT-4 Turbo: no edit command, 7.7 points lower; edit without the syntax check, 3.0 lower; a 30-line file window, 3.7 lower; the whole file, 5.3 lower. Search that stepped through matches one at a time cost 6.0, more than having no search tool (2.3), because agents looked through every match ([Section 5.1](https://arxiv.org/html/2405.15793#S5.SS1)).
- **Agents succeed quickly and fail slowly.** Resolved runs finish earlier and cheaper. An edit attempt eventually succeeds 90.5% of the time, but only 57.2% after one failed edit ([Section 5.2](https://arxiv.org/html/2405.15793#S5.SS2)).

## Where it is weak

- Two models, GPT-4 Turbo and Claude 3 Opus, with ablations on GPT-4 Turbo alone.
- Each ablation is one run. Six runs of the main configuration on Lite resolved between 17.33% and 18.67% ([B.5](https://arxiv.org/html/2405.15793#A2.SS5)). Weigh smaller gaps against it.
- The interface was tuned by hand on "a small set of hand-picked examples" ([Section 4](https://arxiv.org/html/2405.15793#S4)), and the settings sweep used 37 development instances ([B.1](https://arxiv.org/html/2405.15793#A2.SS1)).
- Cost is averaged over resolved issues only ([Section 4](https://arxiv.org/html/2405.15793#S4)), though failed runs are the long, costly ones. P5, in S09, puts cost next to accuracy.
- SWE-bench comes from the same group (reference 20 shares most authors).
- B3 argues for plain bash; S09 lets your numbers decide.

## What it means for your harness

`agent.py` is close to the paper's shell-only baseline. Against Section 2:

- **Concise feedback.** `run_bash` returns everything the command printed. S05 caps it.
- **Compact actions.** Editing through bash takes several commands and is silent: nothing confirms the change. S07 and S08 add `view_file`, `search` and `edit`.
- **Guardrails.** Nothing checks an edit. S08's edit refuses a missing or ambiguous match and says what to do next.

For S07's `view_file` window, Table 3 has the only number: 100 lines beat 30 and the whole file, for one model.

SWE-agent's edit replaces a line range, yours an exact string, so the linting result does not carry over. Its error-message finding does: show the error, the proposed edit and the original lines, as all three helped ([file editor](https://arxiv.org/html/2405.15793#A1.SS1.SSS0.Px2)).

## In their words

Quotes: Yang et al., 2024, CC BY 4.0.

> "Simple commands with a few options and concise documentation are easier for agents to use, reducing the need for demonstrations or fine-tuning."
>
> Source: [2 The Agent-Computer Interface](https://arxiv.org/html/2405.15793#S2)

> "High quality feedback should provide the agent with substantive information about the current environment state (and the effect of the agent's recent actions) without unnecessary details."
>
> Source: [2 The Agent-Computer Interface](https://arxiv.org/html/2405.15793#S2)

> "Deciding whether to introduce a guardrail depends on how well it reduces common model errors compared to whether such restrictions hamper models' preferred workflows."
>
> Source: [A.1, File editor](https://arxiv.org/html/2405.15793#A1.SS1.SSS0.Px2)
