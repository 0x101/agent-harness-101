## In one paragraph

Vivek Trivedy of LangChain defines the **harness** as everything in an agent that is not the model: the system prompt, tools and their descriptions, the environment the code runs in, the logic that starts helpers, and hooks that run at fixed points. The post starts from what you want an agent to do, such as keep state, run code and keep going on long tasks, and names the harness part that makes each one possible. Its slogan is Agent = Model + Harness.

## What it shows

A definition and a map, not a study: almost all of it is the author's view.

- **What counts as harness.** A model alone cannot keep state, run code, reach current knowledge or set up an environment, so each becomes a harness feature (*Why Do We Need Harnesses*).
- **Bash as the general tool.** With bash, the model can write the tool it needs instead of being limited to a fixed set (*Bash + Code as a General Purpose Tool*).
- **Context is a budget.** Models get worse as the context window fills, which the post calls **context rot**. Its answers: **compaction** (summarising a nearly full window), moving large tool outputs to a file, and skills that load only when needed (*Battling Context Rot*).
- **Harness changes move rankings.** LangChain's coding agent went from Top 30 to Top 5 on Terminal Bench 2.0 by changing only the harness (*The Coupling of Model Training and Harness Design*). The result is from an earlier post.

## Where it is weak

- Nothing is measured here. Context rot is asserted, and the Terminal Bench claims give ranks but no scores.
- It is a vendor post that promotes LangChain's deepagents library and LangSmith.
- The components are not derived from anything testable. They are features of current products, each with a reason.
- It makes bash the general tool, while P1 in S04 measures purpose-built commands beating a plain shell. S09 tests both on your tasks.

## What it means for your harness

The starter is B3's harness at its smallest: a system prompt (`SYSTEM`), one `bash` tool, a loop and a step cap. Most of B3's list arrives later:

- **Offloading tool output** in S05: keep the head and tail, say how to see the rest.
- **Compaction** in S16. Until then a full context ends as B3 warns: the API refuses the call and `run` returns `api_error`.
- **Planning** in S19, **subagents** in S24, **verification** in S27, **instruction files** like AGENTS.md in S29, **skills** in S41.
- **No sandbox.** `run_bash` uses `shell=True` wherever you start it; S01 says to use a Codespace or the dev container.

When a baseline task fails, name the missing part you blame, then check the trajectory in S03.

## In their words

> "A harness is every piece of code, configuration, and execution logic that isn't the model itself."
>
> Source: [Can Someone Please Define a "Harness"?](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness)

> "The harness keeps the head and tail tokens of tool outputs above a threshold number of tokens and offloads the full output to the filesystem so the model can access it if needed."
>
> Source: [Battling Context Rot](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness)

> "Deciding where the agent runs, what tools are available, what it can access, and how it verifies its work are all harness-level design decisions."
>
> Source: [Sandboxes and Tools to Execute & Verify Work](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness)
