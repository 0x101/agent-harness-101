## In one paragraph

mini-SWE-agent comes from the Princeton and Stanford team behind SWE-bench and SWE-agent. Its README asks whether an agent 100 times simpler could still work nearly as well. It has one action, a bash command, and does not even need the model's tool-calling interface. Each command runs in a fresh process, and the history is **linear**: each step only appends, so the messages sent to the model are also the record of the run. The README claims about 100 lines for the agent class and a score above 74% on SWE-bench Verified.

## How to read it for this course

About 25 minutes. This guide reads the main branch (version 2) as of 19 November 2026. It moves, so look for names, not line numbers.

- **Read closely:** in the [README](https://github.com/SWE-agent/mini-swe-agent), the two collapsed "More motivation" sections and "Should I use SWE-agent or mini-SWE-agent?". Then [`agents/default.py`](https://github.com/SWE-agent/mini-swe-agent/blob/main/src/minisweagent/agents/default.py): `AgentConfig`, `run`, `step`, `query` and `execute_actions`.
- **Skip:** the install options, the news lines and `serialize`.
- **S09, Checkpoint: the minimalist's challenge.** Read `default.py` beside your `harness/agent.py`, which by now has truncation, `view_file`, `search` and `edit`. List what mini-SWE-agent leaves out, then ask your ablation whether you needed it.

## What it shows

The code is fact. The README's performance claims are the authors' own.

- **The loop.** `run` builds a system and a task message from templates, then calls `step` and saves the trajectory until the last message has the role `exit`. `step` is `execute_actions(query())`, and `execute_actions` sends each action parsed from the reply to `env.execute`.
- **Limits before every call.** `query` checks a step limit, a cost limit and a wall-clock limit, and raises `LimitsExceeded` or `TimeExceeded` carrying an `exit` message. Then it calls the model and adds the reported cost. A limit of 0 means none. In the `AgentConfig` defaults only the cost limit is on, at 3.0.
- **How a run ends.** `default.py` makes an `exit` message for a limit, for three format errors in a row (the default), and for an uncaught exception, which is recorded and raised again. A normal finish comes from the environment: in `environments/local.py`, a command whose first line of output is `COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT` raises `Submitted`, which carries the `exit` message.

Against `agent.py`: both start a fresh process for each command and append everything to one list. But `agent.py` gets parsed `tool_use` blocks, so it has no format errors. It finishes when a reply asks for no tool. It caps steps (`MAX_STEPS`, 30) and counts tokens, not cost. And it logs JSONL events instead of saving the message list each step.

## Where it is weak

- The score above 74% names no model, date or cost, and "nearly as well" is never measured.
- The authors describe their own tool.
- The 100-line count covers the agent class only. Parsing actions, running commands and formatting output live in other classes, so whether long output is cut is not decided in `default.py`.
- The case for dropping tools is experience: models became more capable. The README reports no ablation. P1, from the same team, argued for the special interfaces this repository drops.

## What it means for your harness

S09's ablation asks the README's question on your 12 tasks: bash plus truncation against your full tool set, each with `--repeat 2`. One flip moves the pass rate 8 points, so a gap of one task is noise.

Two ideas are worth taking either way. First, limits inside the loop: your runner's `--budget-usd` caps spend across eval runs, but inside `agent.py` only `MAX_STEPS` stops a task. S11 adds a wall-clock limit, which leaves cost as the one check in `query` you lack. Second, count every billed call, even one whose reply you discard, as the comment below does.
