## In one paragraph

Anthropic's post argues that a **tool** is a contract between ordinary code, which behaves the same way every time, and an agent, which does not. So you design tools for the agent, not as an API for another programmer. The post gives a process: build a prototype, evaluate it on realistic tasks, read the transcripts, and let an agent help improve the tools. It ends with five principles: choose a few well-aimed tools, namespace them, return meaningful context, keep responses small, and write descriptions with care.

## What it shows

Mostly the authors' experience. Their evaluation results appear only as charts, with no numbers in the text.

- **Fewer, better-aimed tools.** Tools that merely wrap existing functions or API endpoints are a common error. Build the tool the job needs: a `search_logs` that returns only relevant lines with some context, not a `read_logs` ([Choosing the right tools](https://www.anthropic.com/engineering/writing-tools-for-agents#choosing-the-right-tools-for-agents)).
- **Small responses that steer.** Use pagination, range selection, filtering or truncation with sensible defaults; Claude Code caps tool responses at 25,000 tokens by default. When you truncate, tell the agent how to do better, and make errors specific and actionable ([Optimizing tool responses](https://www.anthropic.com/engineering/writing-tools-for-agents#optimizing-tool-responses-for-token-efficiency)). In a Slack example, a concise response took 72 tokens and a detailed one 206 ([Returning meaningful context](https://www.anthropic.com/engineering/writing-tools-for-agents#returning-meaningful-context-from-your-tools)).
- **Descriptions are prompts.** After precise refinements to tool descriptions, Claude Sonnet 3.5 reached state-of-the-art on SWE-bench Verified ([Prompt-engineering your tool descriptions](https://www.anthropic.com/engineering/writing-tools-for-agents#prompt-engineering-your-tool-descriptions)). Claude also kept adding 2025 to web search queries until the description was improved ([Analyzing results](https://www.anthropic.com/engineering/writing-tools-for-agents#analyzing-results)).

## Where it is weak

- A model vendor writing about its own model. The charted gains are on its internal Slack and Asana tools.
- The SWE-bench claim gives no score, no baseline, and no word on which change mattered.
- The evidence comes from Anthropic's internal workspace, not coding tasks, apart from that one line. Most of the advice came from optimizing tools with Claude Code itself.
- Namespacing has "non-trivial effects", without numbers.
- It sits against P2, which makes code the action, and B3, which makes bash the general tool. S06 makes you pick; S09 measures.

## What it means for your harness

The starter's only tool description is one line: "Run a bash command in the repository and return its exit code, stdout and stderr." Its parameter, `command`, has no description. By A2's standard that is thin, and it is all the model knows.

- **S05.** Truncation with a note on how to see the cut lines is A2's token advice.
- **S06.** `search(pattern, path)` is the `search_logs` idea; `06-needle-in-logs` is the obvious task to watch. Name parameters so they cannot be misread, as A2 prefers `user_id` to `user`.
- **S07.** `view_file(path, start, end)` is range selection, and capped `search` results are a sensible default.
- **S08.** An edit error that reports zero matches, or lists the line numbers of several, is an actionable error.
- **Measuring.** A2 collects tool calls, tokens and tool errors, not only accuracy. Do the same from your trajectories.
